==============================================================================
Endpoint Routing + Host Strategy
==============================================================================

Your client should treat "host selection" as a first-class concern:

1) Unauthenticated, public reads (fast path)
   - Base URL: https://public.api.bsky.app
   - Use for: browsing without login (profiles, public feeds, threads, search)
   - Bluesky docs explicitly call out that many public app.bsky.* endpoints can be
     called directly against the public AppView API.

2) Authenticated requests (normal logged-in mode)
   - Base URL: the user’s PDS (discovered from identity resolution)
   - Why: authenticated requests are “usually made to the user's PDS, with automatic
     service proxying” (and can include extra metadata/filtering).

3) Service proxying (chat + some services)
   - Make the request to the user’s PDS, and set the service proxy header to target
     the downstream service. Bluesky chat endpoints explicitly require proxying to
     did:web:api.bsky.chat.
   - The service-proxying mechanism is specified in the AT Protocol XRPC HTTP spec.

Auth note (opinionated):
- Prefer OAuth for a real end-user app (mobile/desktop). The AT Protocol OAuth spec
  is the authoritative reference, and Bluesky also publishes an implementation guide.
- Keep the legacy session endpoints available for dev-mode / app-password support.

Endpoint Map (by Feature)
==============================================================================

Legend:
- Host: AppView = https://public.api.bsky.app, PDS = user’s PDS base URL
- Auth: None | User
- Proxy: (blank) or “Proxy: chat” meaning service-proxy header targeting chat service

------------------------------------------------------------------------------
Identity + Sessions
------------------------------------------------------------------------------

Resolve handle -> DID
  NSID:  com.atproto.identity.resolveHandle
  HTTP:  GET /xrpc/com.atproto.identity.resolveHandle
  Host:  PDS (recommended; servers may cache)
  Auth:  None

Resolve DID -> DID document
  NSID:  com.atproto.identity.resolveDid
  HTTP:  GET /xrpc/com.atproto.identity.resolveDid
  Host:  PDS
  Auth:  None

Resolve identity (handle or DID) -> DID doc + verified handle
  NSID:  com.atproto.identity.resolveIdentity
  HTTP:  GET /xrpc/com.atproto.identity.resolveIdentity
  Host:  PDS
  Auth:  None

Legacy login (app passwords)
  NSID:  com.atproto.server.createSession
  HTTP:  POST /xrpc/com.atproto.server.createSession
  Host:  PDS
  Auth:  None (but uses password in body)

Check current session
  NSID:  com.atproto.server.getSession
  HTTP:  GET /xrpc/com.atproto.server.getSession
  Host:  PDS
  Auth:  User

Writing (posts, likes, reposts, follows) — repo writes
------------------------------------------------------------------------------

Create a record (generic write primitive)
  NSID:  com.atproto.repo.createRecord
  HTTP:  POST /xrpc/com.atproto.repo.createRecord
  Host:  PDS
  Auth:  User

Update a record
  NSID:  com.atproto.repo.putRecord
  HTTP:  POST /xrpc/com.atproto.repo.putRecord
  Host:  PDS
  Auth:  User

Delete a record
  NSID:  com.atproto.repo.deleteRecord
  HTTP:  POST /xrpc/com.atproto.repo.deleteRecord
  Host:  PDS
  Auth:  User

Batch writes (atomic-ish UX: post + like, etc.)
  NSID:  com.atproto.repo.applyWrites
  HTTP:  POST /xrpc/com.atproto.repo.applyWrites
  Host:  PDS
  Auth:  User

Upload media blob (images, etc.)
  NSID:  com.atproto.repo.uploadBlob
  HTTP:  POST /xrpc/com.atproto.repo.uploadBlob
  Host:  PDS
  Auth:  User

Practical collections you will use with createRecord/putRecord/deleteRecord:
  - Post:    collection=app.bsky.feed.post
  - Like:    collection=app.bsky.feed.like
  - Repost:  collection=app.bsky.feed.repost
  - Follow:  collection=app.bsky.graph.follow
(These are “record types”; the write endpoints above are the mechanism.)

==============================================================================
Local-only Features (no network endpoints)
==============================================================================

Smart folders (feed views)
  - Definition: locally stored queries over cached timeline/threads + local labels
    Example folder rules:
      - “Unread” (not seen locally)
      - “From follows only”
      - “Mentions + keyword”
      - “Media only”
      - “Saved”
  - Inputs (network): whatever you choose to cache (timeline/author feed/thread/etc.).
  - Output: purely local projection; no server-side “custom feed generator” required.

Local post drafts
  - Stored in Drift only; not published until you call repo.createRecord/applyWrites.
