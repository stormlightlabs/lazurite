================================================================================
Principles + References                                              *bsky-prin*
================================================================================

Architecture principles:
- Separation of concerns: UI layer vs Data layer, with clear boundaries.
- Feature-first organization inside those layers (each feature owns its
  domain/data/presentation).
- Cursor-based pagination everywhere (avoid OFFSET paging for feeds).

ATProto / Bluesky host rules (source of truth):
- Public endpoints can be called directly via https://public.api.bsky.app.
- Authenticated requests are usually made to the user’s PDS with automatic
  proxying.
- Service proxying is controlled by an HTTP header
  ("Atproto-Proxy/atproto-proxy") and specified in XRPC.

OAuth (mobile client reality):
- atproto OAuth profile mandates DPoP and uses PAR in the initial auth request.

DMs (Chat service):
- Chat requests go to the user’s PDS and are proxied to did:web:api.bsky.chat
  via service proxy header.

Drift:
- Drift is the primary relational persistence library for Dart/Flutter; supports
  reactive queries and isolates.

Secure secrets:
- Store tokens/keys in secure storage, not Drift (e.g. flutter_secure_storage).

G. Multi-feed support + preferences sync                                *bsky-G*
================================================================================

Summary: Multi-feed architecture enables users to browse, save, and switch
between custom algorithm feeds. User preferences (savedFeedsPref) are the
canonical source of truth, synced via getPreferences/putPreferences. Local
SavedFeeds table caches remote preferences enriched with feed metadata.

Endpoints:
- app.bsky.actor.getPreferences (GET) - fetch user preferences including saved
  feeds
- app.bsky.actor.putPreferences (POST) - update user preferences (full object)
- app.bsky.feed.getFeed (GET) - fetch posts from a custom feed URI
- app.bsky.feed.getFeedGenerator (GET) - fetch metadata for a specific feed
- app.bsky.unspecced.getPopularFeedGenerators (GET) - discover trending feeds

Tasks:
- [x] Data layer:
      - [x] Create SavedFeeds Drift table (uri, displayName, description,
            avatar, creatorDid, likeCount, sortOrder, isPinned, lastSynced)
      - [x] Update TimelineRepository.fetchAndCacheTimeline to accept optional
            feedUri parameter
      - [x] Derive feedKey from feed URI for database storage
      - [x] Seed default feeds: Home (authenticated) and Discover (public)
- [x] FeedRepository:
      - [x] syncPreferences: fetch savedFeedsPref from getPreferences, hydrate
            local cache with metadata from getFeedGenerator
      - [x] saveFeed: add URI to savedFeedsPref array, push via putPreferences,
            update local cache
      - [x] removeFeed: remove URI from both local and remote storage
      - [x] discoverFeeds: fetch trending feeds from getPopularFeedGenerators
      - [x] Ensure putPreferences sends entire preferences object to avoid
            overwriting other preference categories
- [x] State management:
      - [x] ActiveFeedNotifier: tracks currently selected feed URI
      - [x] SavedFeedsNotifier: watches SavedFeeds table, exposes pinned feeds
            in sort order
      - [x] TimelineNotifier listens to active feed changes, reloads content
            and clears items/cursors on feed switch
- [x] UI components:
      - [x] FeedSelectorTab: horizontal tabs for pinned feeds with icons/names
      - [x] FeedDiscoveryScreen: trending feeds with preview and save actions
      - [x] FeedManagementScreen: reorderable list, unpin actions
      - [x] Integrate feed selector into TimelineScreen header
      - [x] AppRoutes / Router
- [ ] Preference syncing:
      - [ ] Sync on app foreground resume to reconcile remote changes
      - [ ] Optimistic updates with background sync retry
      - [ ] Queue preference updates offline, retry on network restoration
      - [ ] Show sync indicator when local state diverges from remote
      - [ ] Refresh stale metadata (lastSynced > 24h) from getFeedGenerator

Tests:
- [x] FeedRepository unit tests: syncPreferences, saveFeed, removeFeed,
      discoverFeeds
- [ ] Preference sync does not overwrite other preference categories
- [ ] Feed switching preserves cursor state per feed
- [ ] Offline feed saving queues updates for background sync
- [ ] Cross-device sync: changes in web client appear after syncPreferences
- [ ] Cache eviction: timeline items for feeds not viewed in 7 days are removed
- [x] Widget tests for feed selector, discovery, and management screens

Deliverables:

- [ ] Saved feeds sync across devices via user preferences

H. Composer + local drafts + publish pipeline                           *bsky-H*
================================================================================

Endpoints (write):
- com.atproto.repo.uploadBlob (POST)
- com.atproto.repo.createRecord (POST)

Tasks:
- [ ] Drafts stored locally (Drift):
      - drafts table (text, reply/quote refs, facets, status)
      - draft_media table (local path, mime, alt text, uploadCid/blob ref)
- [ ] Draft UX:
      - autosave and recover
      - "publish later" is a first-class state
- [ ] Publish pipeline:
      (1) upload blobs (if any)
      (2) build post record payload
      (3) createRecord (collection app.bsky.feed.post)
      (4) mark draft posted (or archive)
- [ ] Failure handling:
      - partial upload failures -> retry UI
      - publish failure -> draft remains editable

Tests:
- [ ] Draft persistence tests (save, load, migrate).
- [ ] Publish pipeline unit tests (uploads then createRecord).
- [ ] "airplane mode" test: drafts still editable and safe.

Deliverables:

J. Smart folders (local-only saved views)                               *bsky-J*
================================================================================

Definition:
- A smart folder is a saved query over cached posts + local metadata.
- It never fetches from network by itself; it organizes what’s already cached.

Tasks:
- [ ] Drift tables:
      - smart_folders (name, sortMode)
      - smart_folder_rules (type, payloadJson)
      - optional smart_folder_items materialization (later)
- [ ] Rule engine (MVP rule types):
      - author allow/deny (DIDs)
      - keyword include/exclude (text)
      - has media / has link
      - bookmarked only
      - exclude replies / replies only
- [ ] UI:
      - create/edit folder
      - folder list and folder detail view

Tests:
- [ ] Rule evaluation tests against fixture posts.
- [ ] Query performance test with N=10k cached posts.

Deliverables:
- "Saved views" that feel like feeds, entirely local and fast.

K. DMs (read + write) + outbox + read-state                             *bsky-K*
================================================================================

DM fundamentals:
- Chat endpoints are called via user’s PDS and proxied to did:web:api.bsky.chat
  via service proxy header, per chat endpoint docs and XRPC proxy spec.

Endpoints:
- chat.bsky.convo.listConvos (GET)
- chat.bsky.convo.getMessages (GET)
- chat.bsky.convo.sendMessage (POST)
- chat.bsky.convo.acceptConvo (POST)
- chat.bsky.convo.updateRead (POST)

Tasks:
- [ ] Dio proxying:
      - add `atproto-proxy` header for all chat.* calls (service proxying).
- [ ] Drift tables:
      - dm_convos, dm_members, dm_messages
      - dm_outbox (local queued sends)
- [ ] Inbox UI:
      - convo list, unread indicators, accept requests flow
- [ ] Convo UI:
      - message list paging
      - compose/send
      - mark read on view (updateRead)
- [ ] Outbox worker:
      - persist pending messages immediately
      - retry sends safely (bounded; user-visible failure state)
      - never double-send without explicit server acknowledgement

Tests:
- [ ] Proxy header unit test: chat.* requests include atproto-proxy.
- [ ] Outbox tests: enqueue -> send -> mark delivered; retry on transient errors
- [ ] UI tests: offline send creates pending bubble; online later resolves.

Deliverables:
- DMs usable end-to-end: read, accept, send, read-state, robust retries.
