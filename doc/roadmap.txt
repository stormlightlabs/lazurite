================================================================================
Principles + References                                              *bsky-prin*
================================================================================

Architecture principles:
- Separation of concerns: UI layer vs Data layer, with clear boundaries.
- Feature-first organization inside those layers (each feature owns its
  domain/data/presentation).
- Cursor-based pagination everywhere (avoid OFFSET paging for feeds).

ATProto / Bluesky host rules (source of truth):
- Public endpoints can be called directly via https://public.api.bsky.app.
- Authenticated requests are usually made to the user’s PDS with automatic
  proxying.
- Service proxying is controlled by an HTTP header
  ("Atproto-Proxy/atproto-proxy") and specified in XRPC.

OAuth (mobile client reality):
- atproto OAuth profile mandates DPoP and uses PAR in the initial auth request.

DMs (Chat service):
- Chat requests go to the user’s PDS and are proxied to did:web:api.bsky.chat
  via service proxy header.

Drift:
- Drift is the primary relational persistence library for Dart/Flutter; supports
  reactive queries and isolates.

Secure secrets:
- Store tokens/keys in secure storage, not Drift (e.g. flutter_secure_storage).

I. Smart folders (local-only saved views)                               *bsky-I*

- It never fetches from network by itself; it organizes what’s already cached.

- Chat endpoints are called via user’s PDS and proxied to did:web:api.bsky.chat
  via service proxy header, per chat endpoint docs and XRPC proxy spec.

Endpoints:
- chat.bsky.convo.listConvos (GET)
- chat.bsky.convo.getMessages (GET)
- chat.bsky.convo.sendMessage (POST)
- chat.bsky.convo.acceptConvo (POST)
- chat.bsky.convo.updateRead (POST)

Tasks:
- [ ] Dio proxying:
      - add `atproto-proxy` header for all chat.* calls (service proxying).
- [ ] Drift tables:
      - dm_convos, dm_members, dm_messages
      - dm_outbox (local queued sends)
- [ ] Inbox UI:
      - convo list, unread indicators, accept requests flow
- [ ] Convo UI:
      - message list paging
      - compose/send
      - mark read on view (updateRead)
- [ ] Outbox worker:
      - persist pending messages immediately
      - retry sends safely (bounded; user-visible failure state)
      - never double-send without explicit server acknowledgement

Tests:
- [ ] Proxy header unit test: chat.* requests include atproto-proxy.
- [ ] Outbox tests: enqueue -> send -> mark delivered; retry on transient errors.
- [ ] UI tests: offline send creates pending bubble; online later resolves.

Deliverables:
- DMs usable end-to-end: read, accept, send, read-state, robust retries.
